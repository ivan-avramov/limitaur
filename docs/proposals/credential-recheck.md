# Credential re-check for paused accounts

Status: proposed, strict four-eyes. Discussion P347. Revision 7: revision 4 after design review rounds 1–3 (marked r4, not design-reviewed), corrections from the change review of candidate 1 (r5), from the verdicts on candidate 2 (r6), and from the verdicts on candidate 3 (r7).

## Goal

Limitaur reads a provider's login token once when an account is connected and keeps that copy in memory. When the copy expires, or the initial read is denied or fails, the account is paused and nothing looks at the source again until the user presses Connect, even though the provider's own app (Claude Code, Codex CLI) has long since written a fresh token. Solving this means: while an enabled account has no usable credential, Limitaur re-reads that account's configured source at a slow, bounded cadence without any user interaction, and resumes polling by itself as soon as a different, unexpired credential appears; it never raises a Keychain prompt, never refreshes or writes a token, and never bypasses an existing provider throttle.

## Scope

- `Sources/LimitaurCore/Monitor.swift`: the re-check trigger behind an explicit driver flag; per-profile last-load instant; a load-origin flag carried through sleep; silent handling of every non-resuming re-check outcome; rejected-fingerprint memory for re-checks; throttle carry-over on attach and protection of a deadline set during a request; Connect precedence; a credential-identity comparison for load completion, pending-load reconciliation and sleep replay; interval validation; one shared pause message constant (`credentialMessage` lives in this file). About 120 lines.
- `Sources/LimitaurCore/Credentials.swift`: no change.
- `README.md`: the automatic-resume behaviour, M1's outcome, and the accepted sensitive areas (r4).
- Regression tests (r6): every r5 and r6 rule has a test in the implementer-authored test file, including the sticky `http401` through a failed Connect, the alias marked on a shared 401, provider change during a pending load, `setProfiles`-driven rejected-pair suppression, `retryDate` on creation, the capacity message transition, the three completion paths above, and the alias re-send case.
- New tests under `Tests/LimitaurCoreTests/CredentialRecheck/` (test-writer) and new test files in existing targets if the implementer needs them. No existing test file changes. No UI, transport, decoder, cadence or settings changes beyond adding a defaulted `driver` parameter to the public `refresh`.

## Settled constraints (operator and specification)

- No background Keychain prompt, ever. Every re-check loads with `interactive: false`: LAContext interaction disabled and the classic Keychain interaction policy set to false around the query (existing `SystemKeychainReader.claudeCredential(interactive:)`).
- No token refresh, no credential writes, no copies into app-owned storage. (r4, corrected) The Keychain item and the Codex file are read whole, as today; only the access token, its expiry and the account id are parsed out and kept; no refresh-token value is extracted, kept or compared, and the raw bytes are released as soon as they are parsed.
- No new timers, polling loops or helpers; the nominal 30-second cycle, wake, dropdown-open and manual refresh are the only drivers.
- Freshness, backoff, single-flight and epoch rules unchanged. Throttle deadlines are never bypassed; this specification extends carry-over to attachment and protects a deadline during a request, which is a stated change to the base throttle rules, not a relaxation (r4: carry-over applies to any active deadline, not only provider-imposed ones; see Sensitive areas).
- Base specification: "explicit refresh/source action clears auth pause" (docs/specification.md). Manual refresh therefore issues a non-interactive re-check regardless of the interval.
- Frozen tests and the measurement collector unchanged. No push.

## Assumptions (designer)

- 300 seconds is the right interval: Claude Code refreshes its token only when it runs, so up to five minutes of delay after that is invisible, and one Keychain read per five minutes is negligible. Injectable for tests.
- A re-check is silent unless it resumes: whatever the read returns short of a usable different credential, it changes no binding, message, health, failure state or cached data, forces no fetch for any entity, and increments only the re-check counter. One exception, chosen so the message never lies: a re-check denied by the Keychain while the account shows the automatic-resume message switches that message once to the existing denied wording. Explicit loads (launch, Settings changes, Connect) keep today's messaging.
- The existing loader is reused with one flag and two small corrections (throttle carry-over on attach; rejected-fingerprint check). Everything else is the trigger.

## Interfaces

- `Monitor.init(..., recheckInterval: TimeInterval = 300)`. A value that is not finite or is below 30 is replaced by 300.
- `lastLoad: [String: TimeInterval]` by profile id, monotonic (continuous clock, counts sleep). Stamped in `beginLoad` for every load actually issued, of any origin, including a wake replay. Never cleared by `detach` or rebind. Removed only in `setProfiles` when the profile is removed, disabled, or its source or expected account changes. A credential-less profile with no entry is stamped with the current instant and skipped; its first re-check is one interval later.
- `rejectedFingerprint: [String: (fingerprint: String, account: AccountID?, serverRejected: Bool)]` by profile id (r6: `serverRejected` entries compare by fingerprint alone; mismatch entries compare the pair). Set for every subscriber removed in `complete()` on either account-mismatch throw (expected-account mismatch, and Codex verified-versus-selected mismatch). Cleared when the profile is removed or reconfigured, when a Connect (`reconnect`) load binds, and when any load binds a different pair (r5). A `setProfiles`-driven explicit load that reads the rejected pair binds nothing and sends nothing, like a re-check (r5: otherwise every Settings save re-sends a rejected token). Consulted by `.recheck` and `setProfiles` loads.
- Load origin. `enum LoadOrigin { case explicit, recheck }` stored in the `loading` tuple. (r4, r5) Pause cause: `Binding` gains `pauseCause: PauseCause?` with cases `http401`, `expired`, `loadFailed` (a Connect in progress is never credential-less, since its load is pending, so no `connecting` case exists). On a 401/403 completion the cause `http401` is recorded on every binding of that entity with the same source and fingerprint, including bindings that are already paused for another reason or paused by a Connect in progress; their pause stays. `http401` is sticky: neither `beginLoad` nor a failed load of any origin overwrites it; only a successful bind clears it. (r6) When a binding marked `http401` is detached for any reason other than a successful bind (for example an explicit load that read a valid credential for the wrong account), its fingerprint is kept in `rejectedFingerprint` as a server rejection, compared by fingerprint alone. (r6) In `complete()`, once the epoch guard has passed, the entity-level effects of the response are applied whatever the subscriber state: a 429 sets the deadline and `retryDate`; a transport or 5xx failure applies backoff; a 401/403 marks `http401` on every binding of the entity with the request's source and fingerprint, paused or not, whatever its generation. Only storing a 200 snapshot, `merge` and the account-mismatch throw still require an eligible unpaused subscriber on the current generation. (r7) The account-mismatch removal keeps `serverRejected == true` for any removed binding that carried `http401`. (r7) Request identity never repeats: an entity's epoch starts from a monitor-wide counter that only increases, so a completion from an entity that was pruned and recreated under the same key cannot pass the epoch guard. (r7) The follow-up refresh after a completion with no eligible subscriber is limited to that entity (`onlyKey`), with the ten-second minimum success age, so other entities keep their cadence. (r6, r7) A re-check or `setProfiles`-driven load never creates or attaches with a fingerprint that any binding of the same provider currently holds with `pauseCause == http401`, or that any `rejectedFingerprint` entry with `serverRejected == true` of a same-provider profile records; it changes nothing but the message transition. Connect may. (r7) A 401/403 marks `http401` on every binding of the entity holding the request's fingerprint whatever its source, and the alternate-credential selection never picks a binding holding that fingerprint.
- Credential identity (r4, r5, r6). Two profile values are **credential-equivalent** when id, provider, source, expected account and enabled state are equal; labels may differ. Because `loaded()` accepts a result only for a credential-equivalent profile and `beginLoad` already checked source and adapter for that profile, no further guard is needed in `loaded()` (r6: the r5 guard was redundant and, if it ever fired, would strand a "Connecting account" row). The `setProfiles` clearing of `lastLoad` and `rejectedFingerprint` uses the same five fields. `setProfiles` keeps a pending load or a sleep-replay entry whose profile is credential-equivalent to the new value, substituting the new label and keeping the origin; `loaded()` accepts a result on the same basis using the current profile.
- Definition. A profile is **credential-less** when it is configured and enabled, has no pending load, and one of: (a) its binding has `authPaused == true`; (b) its binding has a known `expiresAt ≤ wallNow` and its entity has no request in flight; (c) it has no binding and `profileFailures[id]?.0 == .unauthenticated`, which in today's code is exactly the credential failures recorded by `loaded()` and the server-verified mismatch recorded by `complete()`. Capacity exhaustion, "Credential source unavailable" and "Connecting account" are `.unavailable` and are never credential-less.
- Drivers (r4). `enum RefreshDriver { case cycle, dropdown, wake, manual, internal }`. The public `refresh(force:minimumSuccessAge:driver:)` gains `driver` defaulting to `.cycle`, so the app's 30-second timer needs no change; `dropdownOpened` passes `.dropdown`, `wake()` `.wake`, `manualRefresh()` `.manual`; `complete()`, `setProfiles` and the post-load refresh pass `.internal`. Re-checks are issued for `.cycle`, `.dropdown`, `.wake` and `.manual` only; `.manual` ignores the interval. Expiry pausing is not gated by the driver: the existing in-loop pause stays on every path, and case (b) pausing at the trigger runs on every path as well.
- Trigger. After `pruneEntities()` and before entities are iterated, for every credential-less profile in sorted id order: case (b) first pauses the binding with the shared pause message, as the in-loop step does today but no longer behind the throttle guard; then, only for a re-check driver, if `awake` and (the driver is `.manual` or `monotonicNow − lastLoad[id] ≥ recheckInterval`), and no re-check has been issued in this pass for the same `source.stableID` (r4: one read per source per pass). (r5) Among the due credential-less profiles of one source, the one with the oldest `lastLoad` is issued (ties by id), so a profile that keeps failing locally cannot starve another; the issued profile's `lastLoad` is stamped, which rotates the choice. increment `eligibilityCounts["credentialRechecks"]` and call `beginLoad(profile, interactive: false, clearPause: false, origin: .recheck)`.
- Silent re-check. For `origin == .recheck`: `beginLoad` changes no message and no `profileFailures`. In `loaded()`: a thrown credential failure changes nothing and does not increment `credentialFailures`; a loaded credential whose (fingerprint, selectedAccountID) pair equals `rejectedFingerprint[id]` changes nothing; (r4) a loaded credential whose pair equals the binding's and is unexpired at completion lifts the pause, clears `pauseCause` and replaces the binding's stored credential with the loaded one so a renewed expiry is kept (r5), unless the cause is `http401`, in which case it changes nothing; (r5) for a binding paused with cause `http401`, the comparison is by fingerprint alone: a loaded credential with the same fingerprint and a different selected account is still the rejected token and changes nothing (base rule: an unchanged token is never resent after 401, by re-check or manual refresh); a lifted binding fetches on the next eligible cycle, not immediately; a loaded credential that fails the local expected-account check changes nothing (the binding and its cache stay); a loaded credential that cannot be attached for capacity changes nothing (capacity is checked before any detach, counting the slot the detach would free when the old entity has no other subscriber and no active throttle, r4), except the message transition below, which still applies (r5). Only a bindable different credential proceeds, as for an explicit load, and additionally increments `eligibilityCounts["credentialResumes"]`. (r4) A loaded credential whose `expiresAt ≤ wallNow` at completion, for any origin, is treated as the `.expired` failure, never bound. Exception (r4): a re-check's result may move the displayed message of a still-paused account, on its binding or in `profileFailures`, between exactly two constants: `.keychainDenied` sets the existing denied wording ("Keychain access unavailable; choose Connect / Authorize"), any other non-resuming result, including a successful read that cannot bind, sets it back to the shared pause message; the `.wake` driver never applies the denied wording, since the login keychain may still be locked. Health and everything else unchanged. (r5) The expiry pause is a transition for unpaused bindings only: it never overwrites an existing `pauseCause` or message.
- Explicit loads are unchanged in behaviour, including Connect on a rejected fingerprint, which binds and requests as today.
- Load completion. `loaded()` accepts a result when the current profile is credential-equivalent to the one that started the load, using the current profile. It clears `loading[id]` only when that entry belongs to the completing load (same epoch); a stale completion returns without any mutation (r4).
- Throttle (r4, r5). When a load attaches a profile to an existing entity, the target entity's `throttleUntil` and `retryDate` become those of the later deadline between its own and the previous entity's for the same source; creation carries `retryDate` alongside `throttleUntil` the same way (r5); no provenance is tracked. `merge()` keeps the later deadline with its `retryDate` (as today) and the maximum `lastAttempt` (new), so a merged entity is not fetched again on the next tick. A completion never lowers a deadline set after its request started: both dispatch sites (the normal dispatch and the 401 alternate-credential dispatch) record the deadline at dispatch; on success, `throttleUntil` and `retryDate` are cleared only if the deadline is not later than the recorded one. (r6) The alternate-credential dispatch after a 401 skips an alternate whose `expiresAt ≤ wallNow`, pausing it with the expiry transition, before choosing an eligible credential.
- Connect precedence. `reconnect(id)`: a pending `.recheck` load is cancelled (its result is discarded by the epoch guard) and the interactive load starts; a pending `.explicit` load returns as today.
- Sleep and wake (r4, simplified). No re-check is issued while asleep. An in-flight re-check is cancelled at sleep and not replayed; `sleepRevalidation` keeps today's shape for explicit loads only, and the wake driver issues a re-check when one is due (the continuous clock counts sleep). Cost: at most one extra interval after a sleep shorter than the interval. A label edit during sleep keeps an explicit replay entry (credential-equivalent) with the new label. A denied read after a long sleep (locked keychain) is silent apart from the message exception above.
- Message. One constant, "Session expired or rejected; resumes automatically after the provider app signs in again", used by the expiry pause, by `credentialMessage(.expired)` and by the HTTP 401/403 pause.
- Statistics. `credentialRechecks` and `credentialResumes` join the sanitized aggregate counts; `.recheck` failures do not count as `credentialFailures`. No identifiers, no token material.

### Success path

Claude binding paused at `expiresAt` with fingerprint F1; `lastLoad` is the Connect instant. Claude Code writes token T2 (F2, future expiry). On the first nominal cycle at least 300 s after that Connect, the profile is credential-less by (a), awake, no load pending: `credentialRechecks` increments, `lastLoad` is stamped, a non-interactive load runs off the main thread under the existing capacity bound. `loaded()` sees F2 ≠ F1 and F2 ≠ rejected: detaches the old binding, carries the old throttle for the same source, creates a new generation and entity (or attaches to an existing one holding T2), increments `credentialResumes`, and, as today after a rebind, issues the entity refresh immediately: one request with T2 if the entity is eligible, or none if it already has a request in flight, succeeded within ten seconds, or is throttled. The bars show Claude again. No dialog appeared, no message flickered.

### Failure path

Same start, Claude Code has not run. The re-check loads T1; the store throws `.expired`; `loaded()` changes nothing; the next re-check is 300 s after this one. No request. If the Keychain denies the app, `.keychainDenied`, the only change is the message switching once from the automatic-resume wording to the existing denied wording, so the user knows Connect is needed. If the user presses Connect while a re-check is in flight, the re-check is cancelled and the interactive load runs; if the user presses Connect first, the pending explicit load suppresses re-checks until it completes.

## Acceptance criteria

R1 Claude default discovery, injected keychain that records the `interactive` flag: an expiry-paused binding gets a re-check one interval after its last load; with the same still-expired token it stays paused, message, health, cache and `credentialFailures` unchanged, no HTTP request is sent, and every re-check call recorded `interactive == false`. A `.keychainDenied` re-check changes only the message, to the denied wording; a later non-denied non-resuming re-check sets it back; the `.wake` driver never sets the denied wording (r4).
R2 Same setup, then the injected keychain returns a different unexpired token: the next due re-check rebinds, `credentialResumes` is exactly 1, and exactly one request with the new token follows immediately when the entity is eligible; when it attaches to an entity with a request in flight or a success within ten seconds, no duplicate request is sent; no further request from the re-check path or the nominal cycle within 30 s (dropdown and manual refresh behave as today). An unexpired throttle deadline for that source is honoured both on creation and on attachment, and a success completing after the attachment does not clear it; a resumed request that completes just before a nominal tick does not cause a second request at that tick when its entity merges into a retained verified entity (r4).
R3 Initial load denied (no binding, health `.unauthenticated`): one interval later a re-check runs; a later keychain success binds and fetches; counters and `interactive` flags as in R1/R2. Profiles failed for capacity or an unavailable source get no re-check. A local expected-account mismatch on a re-check changes nothing; capacity exhaustion on a re-check leaves the previous binding and cache in place.
R4 Cadence and isolation: no re-check before `recheckInterval` measured from the profile's last issued load of any origin; a wall jump with unchanged monotonic time causes none; a rebind does not reset the interval to zero; a pending explicit load suppresses re-checks; none is issued while asleep; an in-flight re-check at sleep is cancelled and not replayed, and wake issues one only if due; re-checks are never issued from `complete()`, `setProfiles` or a load's own completion refresh, nor from the public `refresh` with `.internal`; the default driver of the public `refresh()` issues them (r4); two profiles on one source get one read per pass; a non-rebinding re-check forces no request on an entity with another healthy subscriber.
R5 Manual refresh issues a non-interactive re-check for every credential-less profile regardless of the interval; the dropdown-open refresh does not bypass the interval. (r4, r5) A pause caused by a failed load or expiry is lifted by a re-check that reads the same unexpired credential; a 401 pause is not lifted by the same token, by re-check or manual refresh, even after a Connect that failed in between (r5).
R6 Connect precedence: Connect pressed during an in-flight re-check cancels it and runs the interactive load, whose result wins; a re-check completing after that cancel changes nothing and leaves Connect's pending entry in place (r4). Connect after a server-verified mismatch binds and requests as today.
R7 Codex 401-paused binding (also: Keychain found-to-absent transition reads the fixed fallback file non-interactively and binds if valid, r4): a file rewritten with the same access token keeps it paused, also when only the selected account changed (r5); a file with a new token resumes it. (r5) An alias paused for a failed Connect whose shared token is then rejected with 401 is marked `http401` and is not lifted by the same token. (r6) A 401 or 429 that completes while a Connect holds the only matching binding paused still marks the rejection or sets the throttle. (r6) A Connect that reads a valid credential for the wrong account after a 401 does not erase the rejection; the restored token is not re-sent. (r6) An alternate credential that expired between a re-check lift and the 401 completion is never dispatched. (r6) A 429 or transport failure completing while a Connect holds the only binding paused still sets the throttle or backoff, and a later same-token lift honours it. (r6) A 401 completing after a Connect that kept the same token on a new generation still marks the rejection. (r6) Two aliases on one source: after the first alias's new token is rejected with 401, the second alias's re-check does not re-send it. (r7) Two aliases paused on a 401-rejected token, Connect on one binds it and the response reports a mismatching account: the other alias's rejection survives and a selector change does not re-send the token. (r7) A profile disabled and re-enabled with the same credential while its first request is held: the held request's late failure, 401 or 200 is discarded, not applied to the recreated entity. (r7) A completion with no eligible subscriber does not cause a request on another entity that succeeded within ten seconds or inside the 30-second cadence. (r7) After the profile holding a rejection is detached by a wrong-account Connect or a capacity refusal, another profile's re-check of the same token sends nothing. (r7) Two profiles on different sources sharing one token: a 401 marks both and the fallback never re-sends that token. A server-verified account mismatch records the rejected fingerprint for every removed subscriber; re-checks returning that fingerprint bind nothing and send nothing; a different token clears it and sends once.
R8 An expired binding whose entity is idle is paused and becomes eligible without waiting for a backoff or throttle to end; an expired binding whose entity has a request in flight is not paused until that request completes, and the completed result is kept.
R9 A label edit during a pending load, with or without an existing binding, and during sleep, neither strands the profile, discards the read, nor issues an extra load; the read keeps its origin and completes under the new label (r4). (r5) A provider change during a pending load discards the read; a credential never reaches another provider's adapter. (r5) Two profiles on one source, one failing locally every time, both get reads in turn; the other resumes. (r5) A same-token re-read with a renewed expiry lifts an expiry pause and the next eligible cycle fetches. A credential that expires between dispatch and completion of a load, including by a forward wall jump, is never bound and never counted as a resume (r4).
R10 (r4) At exactly the entity capacity, a paused sole-owner binding can still resume because the detach frees its slot. Presentation actions still cause no credential read (existing presentation tests unchanged). Original 133 recorded tests, later native tests, frozen suites and collector tests pass unchanged, including when run three times in a row.
R11 No token, fingerprint or path appears in messages, statistics or test output. `recheckInterval` of 0, −1, NaN or 10 behaves as 300.
M1 Manual, on the operator's machine, signed build authorised with Always Allow: let the Claude token expire and run Claude Code; on the first nominal cycle after the interval has elapsed since the last load, plus lookup latency, so within about one interval plus one cycle, Limitaur resumes without any dialog (r4 wording). If the rewritten Keychain item no longer trusts the app, the account shows the denied wording within one interval and README records that automatic resume works for file sources while the Keychain source needs Connect.

## Non-goals

File-system watching; token refresh; changes to the interactive Connect load itself; Keychain ACL changes; new UI; per-provider intervals; retry of HTTP failures (unchanged backoff); clearing a pause whose token is unchanged (base specification: a 401 pause lifts only on explicit reconnect or a changed fingerprint).

## Sensitive areas, named and accepted

- The process-wide classic Keychain interaction policy now flips to false around a query every five minutes per paused Keychain account instead of only at launch and Connect. The existing lock serialises it; an unanswered Connect dialog holds that lock and one of eight capacity slots until answered. Accepted: bounded, no new permission.
- A user-configured credential file under a privacy-protected folder (TCC) can raise a privacy dialog on first access. For a configured file path a re-check is never the first access: an explicit load at launch, Settings or Connect precedes it, so a dialog during a re-check can only follow the user resetting privacy permissions while the app runs. For Claude default discovery, the fallback file is the fixed path `~/.claude/.credentials.json`, read only when the Keychain item is absent; it lies outside the privacy-protected folders, and a re-check may be its first access after the item disappears (r4). Accepted and noted in README; the goal's "never raises a Keychain prompt" is the guarantee, privacy dialogs are outside it.
- (r4) Carrying any active throttle deadline on attachment means a healthy account that already holds the new token can inherit up to 15 minutes of another source's transport backoff in a rare interleaving. Accepted as conservative: it delays, never bypasses, and avoids tracking deadline provenance through backoff, merge and creation.
- (r4) A user-configured credential file on a network, removable or iCloud volume can hang `open()`; today only explicit loads can do that, re-checks make it periodic. Each hung read holds one of eight capacity slots until it returns; eight such profiles would block Connect for every account. Accepted and noted in README; the existing capacity bound is the protection.
- (r4) Re-checks raise how often the whole credential item, refresh token included, passes through process memory, from launch and Connect to once per interval per paused source. Accepted; the bytes are released after parsing and nothing beyond the access token, expiry and account is kept.

## Open questions, resolved by design review

1. Interval: 300 s. Both reviewers concurred.
2. Pauses holding a still-valid token: resolved by the pause-cause rule above (r4). A declined Connect, a half-written file read as malformed, or a forward clock jump lifts on the next re-check that reads the same unexpired credential; only a 401 pause waits for a different token, as the base specification requires.

## Declined for the operator's record

- A "next re-check due" field in the dropdown (opus, round 3, scope request): not needed by the goal.
- Dropping the two counters (opus, round 1): they are the cadence oracles the tests use.
