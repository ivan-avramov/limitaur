## Goal

Seven small backlog items, each with its own narrow problem. The statistics counters report a false eligibility violation every cycle under a learned interval above about 70 s (R-B6). The specification, README and performance notes still describe a 30-second cadence and a literal 90-second freshness (P398). A nudge setting stored as a string reads as on (R-C10). Two Limitaur processes can run at once (R-C5). After an authentication failure the bars can keep ranking a throttle-retained snapshot for up to 300 s while the row says authentication is required (P385); the operator prefers a blank slot to stale data. Two credential/setting paths lack tests (R-C11, P353). Solving this means each item behaves as stated below, nothing else changes, and every existing suite, frozen ones included, passes unchanged.

## Settled constraints

- Operator (P526, P548): blank rather than stale data in the bars; these items in one light run.
- Project: AGENTS.md; frozen suites are never edited; no change to credential reading, writing or the nudge invocation; normal fill tint and thresholds unchanged.

## Assumptions (designer's)

- P385 is a presentation-retention change: it changes how long a cached snapshot is shown and touches no authentication state transition, so the run is light; the change review checks that the authentication branches are unchanged.
- An advisory `flock` on a file in the app's own Application Support directory is enough to keep one menu-bar instance per user; it is released by the kernel when the process exits, so a crash cannot leave a stale lock. The guard is not a security boundary: when the lock cannot be taken for a reason other than another holder, the app runs unguarded (fail open) rather than not at all.

## Specification

1. R-B6 (Sources/LimitaurCore/Monitor.swift). In `defaultWorkloadEligible` and in the `validUntilContinuousNanoseconds` computation of `statistics()`, the literal `success + 90` becomes `success + entity.freshnessHorizon` (the horizon stored at the last success: 90 without a policy, `max(90, interval + 20)` with one). Nothing else in eligibility changes. docs/proposals/session-continuity.md's sentence that `statistics()` and `defaultWorkloadEligible` keep the literal 90 gets a one-clause amendment naming this change (H1).
2. P398 (documentation only). docs/specification.md A7 and docs/performance.md (its first paragraph) describe the qualifying workload at the learned refresh interval (30–120 s, starting at 50 s) instead of a 30-second nominal refresh, and keep "no auth pauses or throttling" with a note that the Claude endpoint's throttling makes a qualifying run unattainable on the operator's machine and that the operator closed the gate on the build 51 smoke (P492/P508). The same two documents state that at the learned cadence the 10-successes-per-provider threshold of A7 can be met at 60 s only with favourable timing (successes at seconds 1, 61, …, 541) and never at a regular 120 s Claude interval; the threshold itself is unchanged. docs/performance.md's later statement of 18 successes as current is corrected to 10 (P487). README's "becomes stale after 90 monotonic seconds" names the horizon exactly: `max(90, interval + 20)` seconds under a learned interval, 90 otherwise. README's measurement procedure gains one clause: quit the running instance first, because a second app-mode launch exits (item 4). README's sentence on `Retry-After` retention gains one clause (r3): unless every profile on the account is paused by an authentication failure, in which case the usage leaves the bars at the normal freshness horizon (item 5). No other README change.
3. R-C10 (Sources/Limitaur/AppUI.swift). The nudge setting is read as `defaults.object(forKey: "claudeNudgeEnabled") == nil || defaults.bool(forKey: "claudeNudgeEnabled")`: absent means on; a stored Bool, integer or string ("NO", "0", "false") is read the way `bool(forKey:)` reads it.
4. R-C5, in-app single-instance guard (operator, P549). A function `takeInstanceLock(directory:) -> InstanceLock` with `enum InstanceLock { case acquired(Int32), held, unavailable }` lives where a unit test can call it with a temporary directory. It applies to `directory` the rules the nudge applies to its directories: create with `mkdir` at 0700 if absent, ignoring the result of `mkdir` (a concurrent creator's `EEXIST` included; r3); then `lstat` it, and only the `lstat` checks decide: a symlink, a non-directory, or a directory not owned by the current user is `unavailable`; a mode other than 0700 is corrected with `chmod`, and a failed `chmod` is `unavailable`. It then opens `directory/instance.lock` with `O_CREAT | O_RDWR | O_NOFOLLOW | O_CLOEXEC` at 0600 (open failure, including a symlinked file: `unavailable`) and calls `flock(LOCK_EX | LOCK_NB)`: success is `acquired(fd)`; `EWOULDBLOCK` is `held` (the descriptor is closed); any other error is `unavailable` (closed). It never unlinks or replaces the file. In the menu-bar app mode (no argument, or `--stats FILE`), `main` calls it with `~/Library/Application Support/Limitaur` after every argument check and before the controller is created: `held` writes `Limitaur is already running` to stderr and exits with status 3 before any monitor, credential read, network request or status item exists; `unavailable` writes `Limitaur cannot take its instance lock; running without it` to stderr and continues; `acquired` keeps the descriptor for the process lifetime. Demo modes and every diagnostic mode take no lock. No Info.plist change.
5. P385 (Sources/LimitaurCore/Monitor.swift). Throttle retention never outlives an authentication failure. Rule, applied where the freshness deadline is computed for showing, ranking and latching (today `freshnessDeadline(_:)` and its three callers: the shown-before check of a completion, the merge latch, and `display()`): while the entity has at least one subscriber and every subscriber's binding is `authPaused` with a non-nil `pauseCause` (`http401`, `expired`, `loadFailed`), the deadline is the nominal one, `successfulInstant + freshnessHorizon`, ignoring `retention` and the in-flight 300 s allowance. Otherwise the deadline is computed exactly as today. Consequences: a snapshot inside its nominal horizon stays shown and ranked until the horizon, never past it; one past its horizon and held only by retention stops being shown and ranked at the next display; a 429 latch while the condition holds cannot extend what is shown (the shown-before check sees the nominal deadline). The rule is state-based, so it covers a pause, a detach that leaves only auth-paused subscribers, and late completions alike. Unchanged: every authentication state transition (when and why a binding pauses, its cause, message, re-check scheduling, the nudge), the stored `retention` value, and the Connect loading pause ("Connecting account", no `pauseCause`), which keeps today's retention. A 200 success clears retention as today; binding changes leave it untouched.
6. R-C11, first half only (tests, plus one product line). Monitor gains the internal accessor `func isNudgeEnabled() -> Bool`. A test toggles the Settings item "Run claude when the Claude session has expired" (rebuilding the Settings menu before each toggle) and polls, bounded, until the monitor's flag matches; both directions. The second half of R-C11 (the live `AppController.init` wiring of `nudger:` and `attemptStore:`) stays in the backlog.
7. P353, the 403 part only (tests only). A test pins that a 403 takes the same path as a 401: the binding pauses with the same message, the entity reports `unauthenticated`, the counter `unauthenticated` increments, and with `reactiveRecheck` a re-read follows (observable as `credentialRechecks` incrementing after the re-check delay). P353's counter-epoch cases stay in the backlog.

## Acceptance criteria

- AC1 (R-B6) With policies of 120 s for both claude and codex, a monitor whose default profiles succeed every 120 s reports `eligible == 1` and `validUntilContinuousNanoseconds` equal to the earlier success plus 140 s (in nanoseconds) at 100 s after the successes, and `violations` unchanged across two cycles; without a policy eligibility ends at 90 s as before (the frozen ThrottleFreshness eligibility test passes unchanged).
- AC2 (R-C10) `claudeNudgeEnabled` absent → on; `true`/`false` Bool → on/off; integer 0 → off, 1 → on; string "NO" → off, "YES" → on.
- AC3 (R-C5) `takeInstanceLock` returns `acquired` for a free lock, `held` while another open in the same process holds it, and `acquired` again after that holder closes; `unavailable` for a symlinked `instance.lock`, a symlinked directory, and a directory path that is a regular file; it corrects a 0755 directory to 0700. Tests never touch the real `~/Library/Application Support/Limitaur/instance.lock` (a live instance may hold it). The designer checks at Accept, by hand, that a second app-mode launch exits 3 with the fixed line while the first runs, and that `--render-demo` and `--version` still run.
- AC4 (P385) With a latched throttle retention past the nominal horizon: a 401 (or 403) after the horizon removes the provider's metrics from `selected` at the next display; a 401 inside the horizon keeps them until the horizon and not after; an expiry pause behaves the same; a 429 arriving while every subscriber is auth-paused does not extend what is shown; the Connect loading pause keeps today's retention; without any authentication event, retention behaviour is unchanged (all frozen ThrottleFreshness tests pass, `nonThrottleFailuresKeepNinetySeconds` included).
- AC5 (R-C11) Toggling the menu item flips the monitor's flag both ways (bounded poll).
- AC6 (P353) 403 and 401 produce identical binding, entity, message and counter state for the same setup, and both lead to a re-read under `reactiveRecheck`.
- AC7 Documentation items of 1 and 2 present; every existing suite passes three times; no frozen file edited.

## Non-goals

Clearing the bars at the first sign of trouble other than authentication; changing retention for throttling alone; P350–P352 behaviour; any change to how credentials are read; relaunch behaviour (R-G1).

## Residuals

- Two different users on one Mac each get their own instance (the lock is per home directory), which is intended.
- A relaunch within about five seconds of quitting can exit 3 while the quitting process waits for a running nudge (it holds the lock until it exits).
- A Finder or `open -n` second launch exits 3 silently (stderr is not visible); a plain `open` activates the running copy.
- After a resume within the original retention window, the retained snapshot can be shown again until that window ends (at most 300 s after its fetch), as for any throttle.
- When the instance lock is unavailable the app runs unguarded.
