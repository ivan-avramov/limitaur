# Provider contracts

Observed locally on 2026-10-18: Codex direct HTTPS `https://chatgpt.com/backend-api/wham/usage` returned snake_case rate windows, optional credits and count-only earned resets. Claude direct HTTPS `https://api.anthropic.com/api/oauth/usage` returned a modern `limits` array; inactive scoped weekly meters still carried valid percentages. These are internal endpoints and are not promised stable APIs.

The [Codex app-server documentation](https://learn.chatgpt.com/docs/app-server) describes an alternative camelCase `rateLimitsByLimitId` shape. The fixture decoder accepts it and gives it precedence over legacy `rateLimits`; default polling uses direct HTTPS. The [Claude Code statusline documentation](https://code.claude.com/docs/en/statusline) describes a separate statusline shape with Unix reset seconds. Limitaur does not fetch statusline data and does not apply that timestamp contract to direct HTTP ISO8601 reset strings.

Codex quota windows use provider-supplied duration and percent. Opaque credit balances remain credit units without inferred currency. Count-only reset metadata has unknown details and expiry. A present invalid modern Codex map is rejected rather than falling back to legacy fields. Claude modern limits keep scope identity, display names and `is_active` meters. Rows with the same stable scope, percent and reset deduplicate even when advisory fields differ. Genuinely different observations for one scope produce one conflicted meter with unknown authoritative usage and reset; the dropdown lists each distinct observed percentage and parsed reset, and that scope leaves ranking. Other scopes remain usable. Opaque extra scope fields contribute only a hash to identity, never raw JSON in normalized output. Legacy utilization is fallback only when modern limits are absent. Unknown future prefix fields are ignored; recognized legacy utilization objects remain supported with neutral labels. Monetary direct-HTTP fields require independently supplied amount, currency and exponent; verified `spend.used` is informational spent amount, never a remaining balance. Unsupported balance or cap semantics remain unknown. Neither adapter invents model-specific limits or transcripts-based usage.

Observed locally on 2026-11-10 (Enterprise team, caller role member; values here are synthetic): Cursor `POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetCurrentBillingCycle` with body `{}` returned `{"startDateEpochMillis":"1700000000000","endDateEpochMillis":"1702592000000"}`; `POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetDailySpendByCategory` with body `{"periodStartMs":"1700000000000","periodEndMs":"1702592000000"}` returned `dailySpend` rows (`day`, `category`, `spendCents`, `totalTokens`), `categories` and `effectiveLimitCents`. Both carry `Authorization: Bearer`, `Content-Type: application/json`, `Accept: application/json` and `User-Agent: Limitaur/1`; responses use proto3 JSON (int64 as digit strings, unset fields omitted). A period with no spend returned only `effectiveLimitCents`; an inverted period was accepted with HTTP 200, so Limitaur requires start < end and at most 62 days; an invalid token returned 401. The adapter sends the cycle request, then the spend request, and decodes both bodies as one envelope; any non-200 response is returned as is. Every row must have a `day` inside the cycle and a `spendCents` integer in 0…2^31−1 (absent means 0), at most 4096 rows; any violation rejects the response rather than giving a partial sum. A positive `effectiveLimitCents` gives metric `spend` (spent ÷ limit, above 100 % kept raw, reset at the cycle end) and the amounts "Spent this cycle" and "Spend limit" in cents ÷ 100, labelled USD by operator decision without a provider currency; an absent limit warns "Spend limit unavailable" and a zero limit "Spend limit is zero", both with no metric. Category names, token counts and day buckets never enter the snapshot. These are private endpoints and may change. Each decoded Cursor snapshot that lists "Spent this cycle" also carries a spend summary (spent, limit or none, USD, cycle end) for the shared budget.

Observed locally on 2026-11-10 (values here are synthetic): Claude `https://api.anthropic.com/api/oauth/usage` returned an enabled `spend` object with typed money, `{"enabled":true,"percent":15,"severity":"normal","used":{"amount_minor":41000,"currency":"USD","exponent":2},"limit":{"amount_minor":500000,"currency":"USD","exponent":2},"cap":{"money":null,"credits":{"amount_minor":500000,"exponent":2}},"balance":null,"auto_reload":null,"disabled_reason":null}`, beside `extra_usage` `{"is_enabled":true,"monthly_limit":500000,"used_credits":41000.0,"utilization":8.2,"currency":"USD","decimal_places":2}`. The response has no reset or period field; the Claude app shows the reset as 00:00 UTC on the 1st of the next month and says reported spend can lag by hours. This supersedes, for the spend fields only, the 2026-10-18 rule that non-null `limit`, `balance` or `cap` warns. An enabled `spend` gives metric `spend` "Monthly spend", resetting at 00:00 UTC on the configured monthly day (Settings → Providers → Claude → Spend resets, default the 1st), and the amounts "Spent this cycle" (`used`) and "Spend limit" (`limit`), each in its own currency. The percent is `extra_usage.utilization` only when `extra_usage` is enabled, its `monthly_limit` and `used_credits` equal `limit.amount_minor` and `used.amount_minor`, its currency equals `used`'s and the utilization is a valid percent; otherwise it is `spend.percent`. A present `limit` that is not valid money warns "Spend limit unavailable"; `cap`, `balance` and `auto_reload` are ignored. The spend summary has `used`, the limit only in `used`'s currency, and the configured reset as its period end. Without `spend`, `extra_usage` is decoded as before.

Offline transport fixtures test a synthetic redirect response and policy callback. They do not verify real TLS/proxy behavior, actual wire redirects, URLSession resource-timeout behavior, cookie/cache interoperability or internal platform retries.
